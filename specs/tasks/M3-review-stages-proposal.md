# M3 offline review-stage design proposal

Status: proposal only, not implemented or paid-authorized. The 22-review allowance is exhausted. The keyed prototype solved this request's missing-ID failure but produced repeated clarification and demonstrably false scope reasons. More complete JSON is not proof of truthful reasoning.

## Proposed offline work

1. Specify an explicit effective-decision record: chosen decision, affected place/group, scope and exact source quotes, retaining original title/description/clarification separately. Confirmed explicit narrowing is represented as a settled choice, not an unanswered question. It remains factual data and cannot override instructions. Offline fixtures may use the author's confirmed lock-only interpretation; do not silently generalize a heuristic to new issues. Contradictions or missing facts remain unresolved rather than forced to match a reference.
2. Centralize and prove the existing scope-compatibility predicate (equal scopes, or building/unit pair) without changing its meaning. Given a validated effective scope, derive genuinely incompatible scope verdicts from immutable issue/reference scope facts. Record origin=scope_rule, both scopes, rule version and source references. This is a fresh explicit proof step, never a retrospective invented reason for a model omission. No automatic semantic/domain exclusion.
3. Design domain/context review only for scope-compatible candidates, then merge explicit scope proofs and model decisions into complete raw-chain coverage. In this fixed building fixture, 19 IDs are scope-compatible and 81 incompatible. These are rule results, not a top-k cap. Similarities, raw chain, alpha/aggregation arithmetic and membership remain unchanged. Every raw ID retains an auditable disposition; all compatible candidates still require a substantive decision.
4. Prevent a compatible reference from being excluded with the scope-mismatch verdict type. Genuine topic/group differences still need factual reasons/evidence; this does not make all 19 compatible references accepted. Preserve literal quotations and the personal-help rule. Never use missing or failed model rows as default exclusions.
5. Test settlement/contradiction, source provenance, full coverage, partial/stale merge refusal and parity with the existing validator offline. Assess input/output envelopes and explain every application integration/migration impact in a new task spec before integration. Keep current embeddings, selection text, library, models, weights and thresholds unchanged for this offline design; alternative selection/query changes require separate review. No provider calls or automatic chunked fallback.

## Important limits and decision

The effective decision/scope can itself be wrong; source checks and a deterministic scope comparison do not prove general semantic understanding. The design must expose that boundary and keep genuine ambiguity visible. It must not force the issue's scope from the nearest reference, silently bypass a clarification gate or relabel earlier model output.

Approve **offline review-stage design and fixtures** above, before any application integration or additional real trial. This approval would authorize design/prototype work only, with no paid calls. No stronger application model is selected or requested here; Sol Medium remains sufficient for the offline work.
