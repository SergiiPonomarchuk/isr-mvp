Approved method, 2026-11-14: author selected preparation of a reviewed helper for the other 27 synthetic profiles, retaining Christine's final Start Voting, option vote and Finish Voting actions in the UI. ## Plan and scope

Implement a dry-run-first Python CLI and Node transaction adapter, using the existing canonical lifecycle/tally helpers. Freeze the registered normal flagship, public membership/ISR maps, exact reviewed options/responsibilities, creator and selected synthetic actors in a durable local plan. Prepare one operation at a time: start-support, option-votes, finish-support. Test pure guards and the complete flow on a dedicated copy. Open a PR with required suites and CI; author merges and runs the helper, with no deployed backend/frontend changes needed.

## Contract

- Explicit project, live acknowledgement, presentation-started execution manifest and separate coalition plan are required. Emulator/live targets must agree at both wrapper and Node adapter. No mocked manifest on live; refuse wrong projects, missing/archived/inactive/expired topics, malformed or changed inputs, noncanonical/duplicate public members and mismatched cached maps.
- Freeze registration time/text/creator, public/membership/ISR fingerprints and both reviewed options, including all creator assignments. Normalize the stored discussion/voting option shapes using title/label, not their volatile tally score. Revalidate inside every apply transaction. Reject altered plans, membership, scores, options or responsibility drift. No user profile, secret, model or geocoder access.
- Select at most 27 other positive-weight public members. Their support alone must stay below the canonical threshold; adding the creator must cross it. Use stored canonical member ISR and Lifecycle management/tally functions, not a new formula. Pin option 0, Emergency Locksmith Service, matching the accepted emulator rehearsal; the plan/preview names it before any author apply.
- Start-support writes only discussion.deadline_votes for selected noncreator actors. Option-votes writes only issue.votes with their normal numeric option indexes. Finish-support mirrors the normal UI's deadline_votes map in discussion and issue. Never write creator input, statuses, dates, messages, options, scores, winner, tally or tasks. The creator's UI action must remain decisive, including quorum for option voting. Server trigger still computes the winner/tasks.
- Preserve unrelated existing inputs; refuse conflicting selected-actor inputs, premature creator input, pre-existing actionable management/quorum, inconsistent voting-stage map copies or a different creator option choice. Refuse to raise the threshold without the creator. Apply is idempotent and atomic, without toggling support. A lost response can resume by inspecting existing maps. After a later phase, an earlier operation returns an explicit phase-advanced/no-write report instead of replaying inputs.
- Default is read-only preview. Record aggregate results/receipts locally, protect the plan with the existing single-writer lock, and never overwrite an existing plan or the live execution journal. Save the plan before returning it. Each operation is a separate author command; no automatic phase progression, background loop, provider request or bulk real-user participation claim.

## Acceptance

1. Dry runs and stale/conflicting inputs write nothing; changed registration/options/member maps/target are rejected. Creator never receives a helper input.
2. Repeated apply of a prepared stage writes nothing; concurrent source changes trigger transactional revalidation. Untouched fields and unrelated votes survive. At most two documents are written per stage.
3. Dedicated emulator copy: prepare support below threshold, execute the actual creator UI transaction to Start Voting, prepare option votes below quorum, execute creator's actual option-vote transaction, prepare Finish support below threshold, execute actual creator UI Finish action and canonical server tally. Verify winner and three creator-assigned tasks, frozen text/time, and untouched source snapshot/copy data. Run drift/conflict/lost-response checks.
4. Required Node/Python suites and final-head CI pass. Read-only live plan may be prepared by the agent after the code is concrete; agent never applies it to production. Author receives exact commands and expected results per stage. Live AC5 is pending until real UI final actions/checker/task review complete.
