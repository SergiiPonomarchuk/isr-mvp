## Model and cost proposal

Pin **gemini-3.1-flash-lite with LOW thinking** for this exploratory candidate run, using the project's existing known integration. This is a proposed fit, not already proven Values-vectorization quality. Do not use the moving gemini-flash-latest alias, silently fall back to another model, change model during a resumed run or deploy a model switch. Gemini2.5 Flash-Lite has a lower listed price, but Google's current model page limits access to projects/users with prior2.5 use; access for this project has not been established. Therefore it is not assumed available or substituted. Batch is cheaper per token but adds a second-stage dependency/asynchronous workflow for just four requests; not proposed for this pilot. Reconsider cost/model after measured pilot quality.

Official sources checked2026-11-23: [pricing](https://ai.google.dev/gemini-api/docs/pricing#gemini-3.1-flash-lite), [model limits](https://ai.google.dev/gemini-api/docs/models/gemini-3.1-flash-lite), [LOW support](https://ai.google.dev/gemini-api/docs/thinking), [2.5 access note](https://ai.google.dev/gemini-api/docs/models/gemini-2.5-flash-lite). Standard text rates used for planning: input$0.25/M tokens, output including thinking$1.50/M. No search/maps/tools, embeddings or explicit cache storage. Recheck rates/model access before any paid request.

Proposed visible maxOutputTokens:4,096 at stage one and8,192 at stage two, with LOW thinking explicitly recorded. A16KiB serialized stage-one output and64KiB complete request limit are proposed admission bounds, not measured real outputs. Stop rather than truncate an oversized narrative/request or raise output limits without review. Thinking tokens may share provider output limits; the runner must verify the current exact request/usage contract and cannot assume LOW is a token cap.

Both byte-to-token conversion and thought margin are planning assumptions; these are not provider-certified hard billing bounds or promised actual cost. The ceiling is the runner's authorization/reservation ledger limit, not a provider billing hard stop. Reviewed implementation must establish acceptable reservation assumptions before any paid approval; if they cannot be justified or requests do not fit, stop and revise the proposal. ## Candidate contract and validation

- Preserve current two-stage Values protocol and canonical version1.0. New generation manifest records unique run/case identity, source narrative hash, source update-time/Values digest, exact model/configuration/prompt and output digests, time and usage. Keep existing protocol vector_id semantics; use the external generation manifest to distinguish runs rather than inventing a schema version or reusing historical timestamps as if recovered.
- Stage one: exactly10 domains,10 grounding/confidence pairs,36 conflict values and four10-element contextual-shift arrays. Validate strict finite numeric types/ranges from the protocol, no booleans; domain/item scores0..100, context shifts-50..50. Grounding levels follow the prompt's rubric (10/15/20/25/30/35/40); domains below25 are null, with zero shifts and neutral conflicts50 where a paired domain is null. Freeze the explicit conflict/domain mapping from the current prompt for validation.
- Stage two: preserve stage-one domain scores, grounding/confidence, conflicts and shifts exactly; reject drift rather than silently overwrite it. Exactly10 item groups with counts18/17/8/18/6/6/21/18/6/27 (145 total). Enforce null propagation and exact lengths before formatting; do not rely on the current formatter's padding/truncation or the legacy validator's permissive all-null lengths. Use a reviewed null codec only, not a schema-repair heuristic.
- Host sets UID/version/hash/fresh generation timestamp and summaries. overall_grounding is the plain unrounded mean of all10 grounding values, including null-valued domains; overall_confidence keeps the current one-decimal mean convention. Reject unknown/free-text/model-supplied metadata rather than persisting it. No narrative/contact/credential text in receipts; request bodies stay in memory. Save only schema-valid numeric candidates and allowed host metadata privately outside the repository; invalid responses retain a digest, fixed failure codes and usage/status only, not raw provider bodies or URLs.
- Reserve budget durably and enforce a single transport send before every provider attempt; exclusive run lock, pin checks and stage checkpoints. No fallback/retry/silent response repair. Use only the existing approved credential-loader mechanism without reading/printing/copying the secret; if an isolated runner cannot use it without relocating a key, stop for the author. Implement/test without loading credentials. Never invoke a real vectorizer CLI or provider during preparation.
- Pure mocked tests cover all invalid schema/range/null cases, unchanged stage-one fields, forged summaries, byte/output caps, no hidden network retry, ledger interruption/unknown usage/resumption, source drift, privacy, exact candidate comparisons and absence of database writes. Mocked and required Node/Python suites plus a later reviewed emulator promotion rehearsal precede any live write. A passing schema alone is not semantic acceptance.
